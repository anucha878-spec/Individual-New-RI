สรุปใน 1 นาที

ระบบ RI ทำหน้าที่ “ส่งรายการที่อนุมัติจ่ายแล้ว” เข้ามาให้ Cenpay ทำจ่ายจริง แล้วดึงสถานะกลับไปอัปเดต

1 · RI (Manual RI)Offset ข้อมูล Actual แล้วอนุมัติที่หน้าจอ EDW-RI-SD005 → SD007/SD008 (repo msa-adwetl)
→
2 · RI → Cenpayเฉพาะขาจ่าย (net_amount < 0) ยิง 02 WS Landing พร้อม Generate batch_oper_no ใหม่ทุกครั้ง
→
3 · Cenpayตรวจ / อนุมัติ / Split Batch / ทำจ่ายผ่านธนาคาร
→
4 · RI ← CenpayRI เรียก 01 WS payment-verification ดึงสถานะกลับ

สิ่งที่ QA ฝั่ง RI ต้องส่งมอบ

  1. ชุดข้อมูลทดสอบ (Batch + รายการจ่าย) ตาม field ที่กำหนด
  2. เอกสารแนบที่มีอยู่จริงในระบบ DMS
  3. ตาราง “รายการทดสอบ ↔ ผลลัพธ์ที่คาดหวัง”
  4. User ที่ใช้อนุมัติฝั่ง RI (ต้องเป็น user จริง)

สิ่งที่มักตกหล่นจนเทสไม่ผ่าน

  • ยอดรวม Header ไม่ตรงกับผลรวม Detail
  • ช่องทางเป็น “โอน” แต่ไม่ส่งข้อมูลธนาคารครบ
  • dmsDocId เป็นเลขสมมติ ไม่มีไฟล์จริง
  • ไม่มีเคสยอดเกิน 2 ล้าน → ไม่ได้ทดสอบ Batch Split
  • ฝั่ง RI ยังไม่มีตัวดึงสถานะกลับ → ทดสอบได้ครึ่งทาง

เส้นทางจริงของข้อมูล RI ก่อนถึง Cenpay

ฝั่งที่คุยกับ Cenpay/PayM คือ Manual RI ผ่านหน้าจอ EDW-RI ใน repo msa-adwetl — ไม่ใช่ core RI ยิงตรง

EDW-RI-SD005ตรวจสอบ + Offset ข้อมูล Actual RI → สถานะ “รอพิจารณาอนุมัติเข้า EDW”
เขียน tx_ri_actual_offset
→
EDW-RI-SD007 / SD008พิจารณาอนุมัติข้อมูลเข้า EDW
จุดนี้คือจุดที่ Generate เลขอ้างอิง + ส่งเข้า PayM
→
PayM (msa-paymentmg)ได้ tx_payment_detail.oper_ref_no = เลขอ้างอิงของรอบล่าสุด
→
ดึงสถานะกลับSyncPayRiBatchService อ่านเลขจาก tx_ri_actual_offset.batch_oper_no

กติกาที่ต้องจำให้ได้ 3 ข้อ

  1. เฉพาะขาจ่ายที่ไปถึง PayM — net_amount < 0 เท่านั้น · ขารับ (net_amount > 0) ไม่ส่ง PayM จึงไม่มีเลขอ้างอิงโดยดีไซน์
  2. Generate เลขใหม่ทุกครั้งที่ส่งเข้า PayM และทับเลขเดิม — ส่งใหม่ = PayM ทิ้งรายการเก่า (ยืนยันโดยเจ้าของงาน 14/08/2026)
  3. แหล่งความจริงเดียวคือ tx_ri_actual_offset.batch_oper_no — tx_ri_offset_transaction ของแถวขาจ่ายมี 0 แถว (ตารางนั้นเกิดจากไฟล์ขา EDW เท่านั้น)

สถานะฝ่ายการเงิน (tx_ri_actual_offset.process_status_paym)

กด/ส่งซ้ำได้เมื่อสถานะเป็น ค่าว่าง หรืออยู่ในชุด 12 / 15 / 18 ซึ่ง spec ระบุชื่อไว้ว่า

  • ส่งข้อมูลเข้าระบบ PayM ไม่สำเร็จ
  • ไม่ผ่านการตรวจสอบ (ฝ่ายการเงิน)
  • จ่ายเงินไม่สำเร็จ
  • ระงับการจ่าย — เพิ่มใน spec 19/08/2026

13 = กำลังทำจ่าย (อยู่ในชุดที่ระบบ poll สถานะ) → ปุ่ม disable กันจ่ายซ้ำ

ต้องเช็ค: โค้ดปัจจุบันมีแค่ 3 id (12/15/18) แต่ spec ลิสต์ชื่อไว้ 4 อัน — ถ้า “ระงับการจ่าย” เป็น id ใหม่ ต้องเพิ่มเข้า SELECTABLE_FOR_FINANCE_IDS

Batch Split — เคสที่ห้ามลืมเตรียม

Cenpay จะแยก Batch อัตโนมัติเมื่อเข้าเงื่อนไข ถ้าไม่มีข้อมูลเคสนี้ = ทดสอบไม่ครบ

เงื่อนไข “ถูก Split”

มีรายการยอด > 2,000,000 บาท
และ
ใน Batch มีมากกว่า 1 รายการ

→ Batch สถานะ BAS (Batch Split)
→ Cenpay แยกเป็น “กลุ่มเกิน 2 ล้าน” กับ “กลุ่มไม่เกิน”
→ เลข Batch ใหม่รูปแบบ CP-TB-20250904-00001_1-2

เงื่อนไข “ไม่ถูก Split”

ทุกรายการไม่เกิน 2 ล้าน
หรือ
มีรายการเดียวใน Batch

→ Batch สถานะ PEN (รอยืนยัน)
→ ทุกรายการสถานะ WCF (รอยืนยันทำจ่าย ฝ่ายการเงิน)

ฝั่ง RI ต้องดึงสถานะกลับเอง

Cenpay ไม่ push สถานะกลับ — ระบบต้นทางเป็นฝ่ายเรียกถาม

API ที่ต้องเรียก

POST /thaisamut/rs/paymentmg/v2/payment-verification

Input: รายการ operRefNo — สูงสุด 300 รายการต่อครั้ง

Output ที่ได้: batchOperNo, batchOperStatus, transactionStatus, targetStatus, chequeNo, chequeIssueDate, chequeExpiryDate, paidDate, batchPaymentNo, reason (กรณี reject)

สิ่งที่ต้องพร้อมฝั่ง RI ก่อน UAT

  • Job หรือหน้าจอสำหรับเรียก API นี้เป็นรอบ
  • ตาราง mapping targetStatus ของ Cenpay → สถานะภายในของ RI
  • วิธีจัดการเมื่อรายการเกิน 300 (แบ่งรอบเรียก)
  • หน้าจอให้ QA ตรวจว่าสถานะอัปเดตกลับมาจริง

ถ้าส่วนนี้ยังไม่พร้อม จะทดสอบได้แค่ “ส่งเข้า” ไม่ได้ทดสอบ end-to-end

Checklist

รายการส่งมอบของ QA ฝั่ง RI

ใช้เป็นรายการติ๊กก่อนแจ้งว่า “ข้อมูลพร้อมทดสอบ”

ข้อมูลทดสอบ

  • ไฟล์หรือชุดข้อมูล Batch + รายการจ่าย ครบตามเมทริกซ์เคส
  • ทุก Batch: totalTransaction และ totalAmount ตรงกับ detail
  • มีเคส Batch Split (รายการเกิน 2 ล้าน + มากกว่า 1 รายการ)
  • ครบทุกช่องทางจ่ายที่ RI ใช้จริง (รวม OVR/BHT ถ้ามีต่างประเทศ)
  • มีเคส WHT และไม่มี WHT
  • มีเคส Negative (400 / 409 / ยอดไม่ตรง)
  • เลข batchOperNo ไม่ซ้ำกับที่เคยส่ง

ของประกอบ

  • เอกสารแนบอัปโหลดเข้า DMS แล้ว และเปิดดูได้จริง
  • User ผู้อนุมัติฝั่ง RI พร้อมใช้งาน
  • ตาราง “รายการทดสอบ ↔ ผลลัพธ์ที่คาดหวัง”
  • ระบุช่วงวันที่และจำนวน Batch ที่จะทยอยส่ง
  • Job หรือหน้าจอฝั่ง RI สำหรับดึงสถานะกลับ พร้อมทดสอบ
  • ตาราง mapping สถานะ Cenpay → สถานะ RI
  • ผู้ประสานงาน + ช่องทางแจ้งปัญหาระหว่าง UAT

ก่อนเริ่ม

ประเด็นที่ต้องตกลงกันก่อน

1 · รูปแบบเลข Batch ของ RI เคลียร์แล้ว

กำหนดเป็น RI-TB-{YYYYMMDD}-{running 5 หลัก} เช่น RI-TB-20260818-00001 (spec EDW-RI-SD007 · suthanee.sa 14/08/2026 · ทดสอบจริงแล้วใน #93290)

ประเด็นที่เหลือ: เลขนี้ถูกส่งเป็น operRefNo ไม่ใช่ batchOperNo — ต้องยืนยันกับ Cenpay ว่าฝั่ง RI ใช้อะไรเป็น batchOperNo ระดับ Batch

2 · ผู้รับเงินนิติบุคคล

ตกลงวิธีใส่ชื่อบริษัทลงช่อง payeeFirstName / payeeLastName ให้ตรงกัน เพื่อไม่ให้ชื่อบนเช็คหรือหน้าจอผิด

3 · การจ่ายต่างประเทศ

ถ้า RI ต้องจ่าย reinsurer ต่างประเทศ ต้องยืนยันว่าใช้ OVR/BHT และต้องมีข้อมูลอะไรเพิ่ม (SWIFT ฯลฯ) — spec ปัจจุบันไม่ได้ระบุ field เฉพาะไว้

4 · แผน UAT ยังไม่มีแถวของ RI

ไฟล์ Plan UAT Cenpay.xlsx (Lot 2 / Lot 3, ช่วง 17/08–16/09/2026) ยังไม่มีรายการประกันภัยต่อ — ถ้า Individual New RI ต้องเข้ารอบนี้ ต้องเพิ่มแถวและกำหนดวันทดสอบ

จำ 5 ข้อนี้พอ

1 · รหัสต้องถูก

กลุ่ม EI · รายการ RIP · ยิงเข้า 02 WS Landing

2 · ยอดต้องตรง

totalTransaction / totalAmount ต้องตรงกับรายการจริงในทุก Batch

3 · ช่องทางโอน = ข้อมูลธนาคารครบ

ขาดตัวใดตัวหนึ่งจ่ายไม่ได้ · พร้อมเพย์ต้องระบุ I/M

4 · ต้องมีเคสเกิน 2 ล้าน

ไม่งั้นไม่ได้ทดสอบ Batch Split ซึ่งเป็นกลไกหลักของ Cenpay

5 · ครึ่งหลังสำคัญเท่าครึ่งแรก

RI ต้องมีตัวดึงสถานะกลับผ่าน 01 WS payment-verification (สูงสุด 300 รายการ/ครั้ง) ไม่งั้นทดสอบได้แค่ทางเดียว
