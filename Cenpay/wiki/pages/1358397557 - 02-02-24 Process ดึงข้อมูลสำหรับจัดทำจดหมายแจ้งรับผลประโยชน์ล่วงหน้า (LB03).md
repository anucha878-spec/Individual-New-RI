## Objectives

Batch Process สำหรับดึงข้อมูลกรมธรรม์ที่เข้าเงื่อนไขรับเงินตามเงื่อนไขกรมธรรม์งวดแรก (แจ้งล่วงหน้า) จากระบบ AS400 และ Irisapp มาเตรียมไว้ในระบบ Cenpay เพื่อให้ฝ่ายปฏิบัติการตรวจสอบและยืนยันก่อนออกจดหมายแจ้งรับผลประโยชน์ล่วงหน้า (LB03)
Batch นี้มีวัตถุประสงค์ดังนี้
- ตรวจสอบสถานะการประมวลผลของรอบเดือนที่กำลังจะดึงข้อมูล ป้องกันการสร้างรายการซ้ำ
- ดึงข้อมูลกรมธรรม์ที่ครบกำหนดรับเงินในเดือนถัดไปจากระบบ AS400 (`OLIS.OLPLTBNF`) และ Irisapp (`temp_ld02_ld03` เฉพาะส่วน LD02)
- ตรวจสอบเงื่อนไขหนี้สินและจำแนกประเภทเงิน (เงินครบกำหนด/เงินทรงชีพ/เงินสมนาคุณ/เงินบำนาญ)
- สร้างข้อมูล Header และ Detail ลงตาราง `tx_letter_summary` และ `TX_LETTER_DETAIL`
- เตรียมข้อมูลให้ฝ่ายปฏิบัติการตรวจสอบผ่านหน้าจอ Header/Detail ก่อนยืนยันออกจดหมายจริง

## Schedule

- ดำเนินการทุกวัน เวลา **01:00 น.** — ดึงข้อมูลของวันที่ปัจจุบัน -1 (T-1) เนื่องจากข้อมูลฝั่ง AS400/Irisapp จะพร้อมใช้งานหลังเที่ยงคืนของวันนั้น (ยืนยันจาก BA 2026-07-22)

## Preconditions

- ฝั่ง AS400 มีข้อมูลกรมธรรม์ที่เข้าเงื่อนไขรับเงินงวดแรกในตาราง `OLIS.OLPLTBNF` ที่ `LTSTAS='C'` (Complete) และ `LTTYPE='69'` (รหัสจดหมาย LB03 ที่เพิ่มใหม่ในระบบ AS400 — ดู Service spec)
- ฝั่ง Irisapp ต้องมีการกดปุ่ม "ดาวน์โหลดข้อมูล LD02" ให้ระบบสร้างข้อมูลลงตาราง `temp_ld02_ld03` ไว้ล่วงหน้าแล้ว (เป็น manual trigger ฝั่ง Irisapp ไม่ใช่ auto-generate — `[TBD]` ต้องยืนยัน SLA ว่าข้อมูลพร้อมก่อนเวลา Batch รันจริงหรือไม่)
- Batch Job ถึงเวลาที่กำหนดให้ทำการรัน (01:00 น.)

| 1 | ดึงข้อมูลกรมธรรม์จากระบบ AS400ให้ระบบดึงข้อมูลจาก AS400 ผ่าน [Service ดึงข้อมูลออกจดหมาย สำหรับจดหมายแจ้งรับเงินผลประโยชน์](http://wiki.thaisamut.co.th/pages/viewpage.action?pageId=1073676353) (SOAP) โดยส่ง parameter:`letter_type = '69'` (รหัสจดหมาย LB03)`gen_status = 'C'` (Complete — ยืนยันจาก BA 2026-07-22)`letter_date` = วันที่ปัจจุบัน -1 (T-1)`letter_date_to` = `[TBD]` — parameter ใหม่ที่เพิ่งเพิ่มเข้า service (รองรับดึงแบบช่วงวันที่) ยังไม่ยืนยันว่า Batch LB03 จะส่งค่านี้เพื่อดึงช่วงวันที่ หรือส่งแค่ `letter_date` วันเดียว (T-1) แล้วอาศัย logic ข้อ 0 ป้องกันข้อมูลซ้ำแทนเงื่อนไขการดึงข้อมูลระบบ AS400 จะ generate ข้อมูลกรมธรรม์ที่เข้าเงื่อนไขรับเงินงวดแรกใหม่ทุกวัน โดยแต่ละวันจะได้ข้อมูลครบทั้งเดือนถัดไปในคราวเดียว (ไม่ใช่ข้อมูลสะสมทีละวัน)Batch ดึงข้อมูลของวันที่ปัจจุบัน -1 (T-1) ตามตาราง Schedule ด้านบนผลลัพธ์ได้ข้อมูลกรมธรรม์ดิบจาก `OLIS.OLPLTBNF` (47 fields) ของกรมธรรม์ที่ครบกำหนดรับเงินในเดือนถัดไป |
| 2 | ดึงข้อมูลกรมธรรม์จากระบบ Irisapp (LD02)ให้ระบบดึงข้อมูลจาก Irisapp ผ่าน [Service ดึงข้อมูลออกจดหมาย สำหรับจดหมาย LD02_LD03 (Irisapp)](http://wiki.thaisamut.co.th/pages/viewpage.action?pageId=1078263909) โดยส่ง parameter `letter_name_abbr = 'LD02'`เงื่อนไขการดึงข้อมูลใช้เงื่อนไขวันที่เดียวกับฝั่ง AS400 คือดึงข้อมูลของวันที่ปัจจุบัน -1 (T-1) ตามตาราง Schedule ด้านบน (ยืนยันจาก BA 2026-07-22)Precondition: ต้องมีผู้กดปุ่ม "ดาวน์โหลดข้อมูล LD02" ฝั่ง Irisapp ไว้ล่วงหน้าแล้ว เพื่อให้มีข้อมูลอยู่ในตาราง `temp_ld02_ld03` (อ้างอิงหน้าจอเดิม [LD02,LD03 หนังสือแจ้งรับเงินผลประโยชน์ตามกรมธรรม์ อุตสาหกรรม](http://wiki.thaisamut.co.th/pages/viewpage.action?pageId=779485507))**ก่อนดึงข้อมูล ให้ Batch ตรวจสอบก่อนว่ามีข้อมูลอยู่ในตาราง `temp_ld02_ld03` หรือไม่** — ถ้ามีข้อมูล ให้ทำการกวาดข้อมูลเข้าระบบ Cenpay ถ้าไม่มีข้อมูล ให้ข้ามการดึงในรอบนั้น (ไม่ถือเป็น Error) (ยืนยันจาก BA 2026-07-22)`[TBD]` Service นี้รับแค่ `letter_name_abbr` ไม่มี parameter ระบุช่วงวันที่/รอบเดือน — ต้องยืนยันกับทีม Irisapp ว่าตาราง `temp_ld02_ld03` เก็บเฉพาะข้อมูลรอบปัจจุบันเท่านั้น หรือมีข้อมูลรอบเก่าตกค้างที่ต้องกรองเพิ่มฝั่ง Cenpay เองยืนยันจาก BA (2026-07-22): **ไม่จำเป็นต้องมีตาราง Clone แยกต่างหาก** เพราะ TX_LETTER_DETAIL ที่สร้างในขั้นตอนที่ 4 เก็บข้อมูล LD02 ที่ดึงมาแล้วไว้ครบอยู่แล้ว ทำหน้าที่เป็นสำเนาของ Cenpay เองในตัว — กรณี user ยกเลิกรายการ (cancel) โดยที่ข้อมูลไม่ได้ผิด ระบบใช้ข้อมูลที่มีอยู่แล้วใน TX_LETTER_DETAIL (แถวที่ถูกยกเลิก) สร้างรายการใหม่ทดแทนได้เลย ไม่ต้องย้อนกลับไปดึงจาก `temp_ld02_ld03` อีก ส่วนกรณีข้อมูลผิดจริงและต้องแก้ที่ต้นทาง (AS400/Irisapp) ก็ต้องรอต้นทาง Generate ข้อมูลใหม่อยู่ดี (ฝั่ง AS400 auto-regenerate ทุกวัน / ฝั่ง Irisapp ต้องกดปุ่มดาวน์โหลดใหม่) ซึ่งเป็นกรณีที่มี Clone ไว้ก็ไม่ช่วยอะไร เพราะข้อมูลที่ Clone ไว้ก็ยังเป็นข้อมูลผิดชุดเดิม จึงสรุปว่าไม่ต้องมีตาราง Clone แยก และสามารถลบข้อมูลออกจาก `temp_ld02_ld03` ได้ทันทีหลังดึงสำเร็จ ไม่ต้องรอ Confirmเดิม **LD02 ไม่เคยถูกเรียกผ่าน service นี้มาก่อน** (มีแต่ LD03 ที่ถูกดึงไปรวมกับจดหมาย LB01 เดิมอยู่แล้ว) การดึง LD02 เข้า LB03 จึงเป็น logic ใหม่ทั้งหมด ไม่มี pattern เดิมให้อ้างอิงโดยตรงผลลัพธ์ได้ข้อมูลกรมธรรม์อุตสาหกรรม (LD02) จาก `temp_ld02_ld03` (32 fields) เพิ่มเติมจากฝั่ง AS400 — เฉพาะกรณีที่มีข้อมูลอยู่ในตาราง ณ เวลาที่ Batch รัน |
| 3 | รวมข้อมูลจาก 2 แหล่ง และจำแนกประเภทนำข้อมูลจาก AS400 (ข้อ 1) และ Irisapp/LD02 (ข้อ 2) มารวมกัน แล้วจำแนกประเภทเงิน: เงินครบกำหนดสัญญา / เงินทรงชีพ / เงินสมนาคุณ / เงินบำนาญประเภทกรมธรรม์: สามัญ / อุตสาหกรรมเงื่อนไขหนี้สิน: มีหนี้สิน / ไม่มีหนี้สิน**Design: แหล่งข้อมูลยอดเงินผลประโยชน์ (2 แหล่ง แยกตาม POLICY_TYPE)****กรมธรรม์สามัญ (POLICY_TYPE = ORD)** — ยอดเงินมาจาก AS400 (OLPLTBNF) โดยแต่ละประเภทเงินมี field แยกตายตัวอยู่แล้ว: LTMTAM → MATURITY_AMT (เงินครบกำหนดสัญญา), LTBOAM → DIVIDEND_AMT (เงินสมนาคุณ), LTRFAM → SURVIVORSHIP_AMT (เงินทรงชีพ), LTPSAM → PENSION_AMT (เงินบำนาญ) — ไม่ต้องจำแนกเพิ่มเติม เพราะ AS400 แยก column ให้ตามประเภทเงินอยู่แล้ว**กรมธรรม์อุตสาหกรรม (POLICY_TYPE = IND/GOV)** — ยอดเงินมาจาก Irisapp (temp_ld02_ld03) ซึ่งมีโครงสร้างต่างจาก AS400: เก็บเป็น field เดียว `dividend_amount` พร้อม field บอกประเภท `dividend_type` (ไม่ได้แยก column ตายตัวเหมือน AS400) — ยืนยันจากจดหมาย LD02 ตัวอย่างจริง (กรมธรรม์ B6047219) ที่แสดง "เงินสมนาคุณ" เป็นยอดเงินที่มาจากช่องทางนี้**ขั้นตอนจำแนก/routing สำหรับข้อมูลฝั่ง Irisapp:** เมื่อดึง dividend_amount + dividend_type มาจาก temp_ld02_ld03 แล้ว ต้อง map ค่า dividend_type ไปยัง column ที่ถูกต้องใน TX_LETTER_DETAIL (เช่น ถ้า dividend_type = เงินสมนาคุณ ให้ใส่ค่าใน DIVIDEND_AMT, ถ้า = เงินครบกำหนดสัญญา ให้ใส่ใน MATURITY_AMT เป็นต้น)**[TBD - สำคัญ]** Service spec ของ Irisapp (pageId=1078263909) ยังไม่ได้ระบุค่า enum/code ที่เป็นไปได้ทั้งหมดของ `dividend_type` — ต้องขอยืนยันกับทีม Irisapp ว่ามีค่าอะไรบ้าง และแต่ละค่า map ไปที่ column ไหนใน TX_LETTER_DETAIL ก่อนเริ่มพัฒนา routing logic นี้ผลลัพธ์ได้ข้อมูลกรมธรรม์ชุดเดียวกันที่จำแนกประเภทครบถ้วน พร้อมสำหรับสร้างเป็น Header/Detail |
| 4 | สร้างข้อมูลลง Header และ Detailให้ระบบสร้างข้อมูลลงตาราง `tx_letter_summary` (ระดับ Header/รอบ) และ `TX_LETTER_DETAIL` (ระดับรายกรมธรรม์) ด้วยสถานะเริ่มต้น **"รอยืนยันสร้างจดหมาย"**ข้อมูลที่จัดเก็บประกอบด้วยMapping Field: สร้างข้อมูล `tx_letter_summary` — ปี/เดือนที่ประมวลผล, ปี/เดือนรอบการแจ้งรับเงิน, จำนวนรายการ, สถานะMapping Field: สร้างข้อมูล `TX_LETTER_DETAIL` — รายละเอียดกรมธรรม์ ผู้เอาประกัน จำนวนเงินรับ/หัก ที่อยู่จัดส่ง ฯลฯ (ดูรายละเอียดฟิลด์ใน [03-08-02 หน้าจอหลัก LB03](http://wiki.thaisamut.co.th/pages/viewpage.action?pageId=1358168468))ผลลัพธ์ข้อมูลถูกจัดเก็บลงฐานข้อมูลเรียบร้อย พร้อมสำหรับหน้าจอตรวจสอบ |
| 5 | แสดงข้อมูลสำหรับผู้ใช้งานตรวจสอบเมื่อ Batch ดำเนินการเสร็จเรียบร้อย ให้ระบบแสดงข้อมูลผ่านหน้าจอสำหรับผู้ใช้งานตรวจสอบก่อนดำเนินการยืนยันสร้างจดหมายผู้ใช้งานสามารถค้นหารายการ ([03-08-02 หน้าจอหลัก LB03](http://wiki.thaisamut.co.th/pages/viewpage.action?pageId=1358168468))ดูรายละเอียดรายกรมธรรม์ ([03-08-02-01 หน้าจอแสดงรายละเอียด LB03](http://wiki.thaisamut.co.th/pages/viewpage.action?pageId=1358168598))Preview หนังสือแจ้งเตือน (PDF)เลือกรายการที่ต้องการยืนยัน/ยกเลิกผลลัพธ์ผู้ใช้งานสามารถตรวจสอบข้อมูลก่อนยืนยันรายการ |
| 6 | บันทึกประวัติการทำงานของ Batchเมื่อจบการประมวลผลแต่ละรอบ ให้ระบบบันทึกข้อมูลลง Log table ที่มีอยู่แล้วของ Cenpay (ใช้ pattern เดียวกับ Batch อื่นๆ ในระบบ เช่น BH031-BH040) — **ยืนยันชื่อตารางจริงแล้ว** เป็น 3 ระดับ:`lg_batch_process` — 1 แถวต่อการรัน Batch #1 หนึ่งครั้ง (ต้อง register `batch_code` ใหม่สำหรับ LB03 กับ master list — `[TBD]` รอ BA/Dev กำหนดรหัส เช่น BH0xx)`lg_batch_trans` — 1 แถวต่อ 1 กรมธรรม์ที่ประมวลผลภายในรอบนั้น (อ้างอิง `batch_process_id`) — **ใช้ field `status='F'` ของตารางนี้เป็นตัวจับสัญญาณ "Error" สำหรับ logic dedup ในข้อ 0** แทนการสร้าง field ใหม่ที่ TX_LETTER_DETAIL`lg_batch_detail` — 1 แถวต่อ 1 ขั้นตอนย่อยของแต่ละกรมธรรม์ (อ้างอิง `batch_process_id` + `batch_trans_id`) ใช้บันทึกรายละเอียดขั้นตอน เช่น ดึง AS400 สำเร็จ/ไม่สำเร็จ, ดึง Irisapp สำเร็จ/ไม่สำเร็จ, สร้าง Header/Detail สำเร็จ/ไม่สำเร็จผลลัพธ์สามารถตรวจสอบประวัติการทำงานของ Batch ได้ทั้งระดับรอบ/ระดับกรมธรรม์/ระดับขั้นตอนย่อย และใช้เป็นแหล่งข้อมูลสถานะ Error สำหรับ dedup logic ได้โดยไม่ต้องเพิ่ม field ใหม่ที่ tx_letter_summary/TX_LETTER_DETAIL |
