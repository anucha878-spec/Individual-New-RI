## Objectives

- เพื่อตรวจสอบเงื่อนไขวันทำการและประมวลผลดึงข้อมูลจากระบบต้นทาง (Source Systems) ทั้ง 2 ระบบโดยอัตโนมัติในวันทำการที่กำหนด
- เพื่อดึงข้อมูลมาล่วงหน้าเป็นเวลา 8 วันทำการก่อนวันทำการสุดท้ายของเดือน (End of Month minus 8 Working Days)
- เพื่อลดความผิดพลาดในการ Run Batch ผิดวัน ซึ่งอาจส่งผลกระทบต่อรายงานงวดการโอนเงินเข้ากองทุนประกันชีวิตของบริษัท

## Process Overview

1. Batch นี้จะตื่นขึ้นมาทำงานทุกวันในเวลาที่กำหนดระหว่างวันที่ 15-25 ของเดือน โดยมีกระบวนการหลัก 2 ส่วนคือ
  1. Date Validation Logic: คำนวณหา "วันที่ประมวลผลเป้าหมาย (Target Date)" ของเดือนนั้นๆ แล้วตรวจสอบว่า "วันนี้ (Current Date)" ตรงกับวันที่เป้าหมายหรือไม่
  2. Data Ingestion Logic: หากตรงกับเงื่อนไข ระบบจะทำการเชื่อมต่อเพื่อดึงข้อมูลจาก 2 ระบบต้นทาง หากไม่ตรงจะจบการทำงานทันที

## Pre-conditions

1. MSA Service: มีข้อมูลวันหยุดของบริษัท, วันหยุดนักขัตฤกษ์ และวันเสาร์-อาทิตย์ ของปีปัจจุบันอัปเดตอยู่ในระบบฐานข้อมูล
2. API/Connection Availability: ระบบต้นทางทั้ง 2 ระบบ (Source System: Claim System, Cenpay : benefitRegister) ต้องอยู่ในสถานะ Online และพร้อมให้บริการ Connection
3. Current Date Check: วันที่ปัจจุบันของระบบ (System Date) ต้องอยู่ระหว่างวันที่ 15 ถึง 25 ของเดือนเท่านั้น

## Process Description

**Step 1: Date Calculation Logic (ตรรกะการคำนวณหาวันทำงาน)**
ระบบจะต้องคำนวณหาวันที่ดึงข้อมูล โดยจะดึงข้อมูลย้อนหลังจากวันทำการสุดท้ายของเดือน 8 วัน โดยมีขั้นตอนดังรูปคำนวณ และขั้นตอนต่อไปนี้
1. ค้นหาวันทำการสุดท้ายของเดือน (Last Working Day of Month):
  1. ตรวจสอบวันสุดท้ายของเดือนปัจจุบัน (เช่น 28, 29, 30, 31)
  2. ตรวจสอบกับ MSA Service : GET:/thaisamut/rs/mastersetting/v1/holiday/{year}/{type} โดยส่งพารามิเตอร์ ปี (ค.ศ.) (YYYY) และ ประเภทของวันหยุด (Fix "HQ") โดยตรวจสอบวันสุดท้ายนั้นเป็นวันหยุดหรือไม่ (วันหยุดเสาร์-อาทิตย์, วันหยุดบริษัท, นักขัตฤกษ์)
  3. หากเป็นวันหยุด ให้ถอยย้อนกลับทีละ 1 วัน จนกว่าจะเจอ "วันทำการแรกที่ไม่ใช่วันหยุด" -> ให้กำหนดวันนั้นเป็น "วันทำการที่ 8"
2. นับย้อนกลับถอยหลัง (Count Backward for 8 Working Days):
  1. จากวันทำการที่ 6 (วันทำการสุดท้าย) ให้ระบบนับถอยหลังย้อนกลับไป โดย "ข้าม (Skip)" ทุกวันที่เป็นวันหยุดเสาร์-อาทิตย์ และวันหยุดตามปฏิทินบริษัท
  2. นับย้อนกลับไปจนครบวันทำการที่ 1, .... , 7 และ "วันทำการที่ 8"
3. กำหนด Target Date:
  1. วันทำการที่ 1 ที่คำนวณได้ คือ "วันที่กำหนดให้ประมวลผล (Target Run Date)"

**Step 2: การดึงข้อมูลและบันทึกข้อมูล**
1. Batch Job ทำงานตามตารางเวลา (ตื่นตอน 22:00 น. ของทุกวันในช่วงวันที่ 15-25)
2. ระบบคำนวณหา Target Run Date ของเดือนปัจจุบันตามตรรกะใน **Step1**
  1. บันทึก Log การทำงานในตาราง [lg_batch_process](/display/RDSCP/Table+%3A+lg_batch_process) สถานะเป็น I
3. ระบบตรวจสอบว่า Current Date (วันที่ปัจจุบัน) = Target Run Date หรือไม่
  1. กรณีไม่เข้าเงื่อนไข ระบบจะทำการจบกระบวนการทันที (Terminate Process) โดยไม่มีการดึงข้อมูล และบันทึก Log การทำงานในตาราง [lg_batch_process](/display/RDSCP/Table+%3A+lg_batch_process) สถานะเป็น S และ total_record = 0
  2. กรณีเข้าเงื่อนไข ระบบเริ่มกระบวนการดึงข้อมูล (Data Ingestion) จาก 3 ระบบต้นทาง
    - ดึงข้อมูลจาก Claim System โดยเรียกใช้ MSA Service: [WS สำหรับดึงข้อมูลสินไหมค้างจ่าย จากระบบ CS](/pages/viewpage.action?pageId=1350796005)[(](/pages/viewpage.action?pageId=1351287417)เชื่อมต่อกับ API : [ข้อมูลประวัติการค้างจ่ายเกิน 10 ปี เพื่อโอนเงินเข้ากองทุนประกันภัย](/pages/viewpage.action?pageId=1322189432))
    - ดึงข้อมูลจาก Cenpay โดยเรียกใช้ MSA Service: [WS สำหรับดึงข้อมูลสินไหมค้างจ่าย สำหรับระบบ Cenpay (](/pages/viewpage.action?pageId=1351287417)เชื่อมต่อกับ API : [สำหรับส่งข้อมูลเงินผลประโยชน์จากทะเบียนรอจ่ายใหม่เกิน 10 ปี เพื่อโอนเงินเข้ากองทุนประกันภัย](/pages/viewpage.action?pageId=1358397721))
4. ระบบตรวจสอบความครบถ้วนของข้อมูลที่ดึงมา จัดเก็บลง Database
  1. ประมวลผลจำนวนรายการและจำนวนเงินรวมทุกช่องทาง และสร้าง Batch เลขธุรกรรมด้วยเงื่อนไข [cf_list_of_value](http://wiki.thaisamut.co.th/display/RDSCP/Table+%3A+cf_list_of_value).group = 'CPH_RUNNING_NO' where name = 'BATCH_FUND_NO'

## Post-conditions & Error Handling

- Post-conditions (Success):
  - รายการ Transaction ใน lg_payment_detail ที่เคยมีสถานะเป็น 'เช็ครอขึ้นเงิน' จะถูกอัปเดตเป็นสถานะ 'เช็คหมดอายุ'
  - ระบบบันทึก Log การทำงานของ Batch Process สำเร็จ
- Post-conditions (Failure) & Error Handling:
  - กรณีเรียก Web Service ไม่สำเร็จ (e.g., Timeout, Connection Error):
  - Action: หากระบบใดระบบหนึ่งใน 3 ระบบเกิด Error หรือ Timeout ระบบจะพยายาม Retry 3 ครั้ง หากยังล้มเหลว ให้หยุดทำงาน, ทำการ Rollback ข้อมูลของวันนั้น และระบบจะบันทึก Log Error Code ในตาราง [lg_batch_process](/display/RDSCP/Table+%3A+lg_batch_process) ด้วยสถานะ F (FAIL)
  - Notification: หากเกิดข้อผิดพลาดติดต่อกันเกิน 3 ครั้ง, ระบบจะส่งแจ้งเตือนไปยัง System Admin
- กรณี Database Update ไม่สำเร็จ:
  - Action: ระบบจะพยายาม Rollback การเปลี่ยนแปลงสำหรับรายการนั้น และบันทึก Log ข้อผิดพลาดร้ายแรง
  - Notification: ระบบจะส่งแจ้งเตือนไปยัง System Admin ทันที
